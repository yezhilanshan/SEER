# 毫米波连续动作实时语义理解与分层事件记忆系统方案书

**版本：v2.3（实时执行与调度修订版）**

> 本版本基于 v2.1 进行收敛式修订，并在 5 Hz 在线更新预算下进一步校正实时执行机制。原则：不再增加新的主干网络，只修正会影响训练稳定性、实时性、职责边界与论文论证闭环的问题。系统仍保持“三个可学习核心模块 + 若干轻量 head/规则”的总体结构。

---

# v2.1 → v2.2 关键变更

1. **Cross-Attention 改为 512 维瓶颈式注意力**：Event Token 保持 LLM 原生维度，雷达特征保持 256 维，只在跨模态注意力内部映射到 512 维，避免 100M 级无必要参数。
2. **Streaming Path 改为固定 Event Prompt**：流式事件状态不再依赖任意用户 Instruction，保证 Event Token 为 query-independent 的客观事件记忆；用户问题仅进入完整 LLM 推理路径。
3. **默认更新频率改为 5 Hz**：20 fps 雷达下，每 4 帧更新一次（0.2 s）；TCN 为 stateful，不重复计算历史。这样与 0.5–1 s 量级语义确认延迟目标一致。
4. **R_fast 不再固定 α=0.9**：改为按物理时间常数计算 `α = exp(-Δt/τ_fast)`，默认 τ_fast≈2 s，更新频率变化时原型时间尺度不漂移。
5. **Propose 与 Verify 完全解耦**：Local/Radar 只负责 Proposal；Candidate 建立后，Confirm 仅由 Semantic Difference、Candidate Stability 与 Maturity 决定。
6. **Stability 改为无参数三时刻统计量**：取消缺乏独立 GT 的 learned Stability Head，避免训练目标不闭合。
7. **Commit Refiner 增加事件相对时间编码，并在 Stage 2 中显式训练 Commit Mode**；增加 streaming/commit 一致性损失。
8. **Point Cloud 默认采用 PointNet**；Point Transformer Lite 仅作为升级/消融项。
9. **Stage 1 改为逐帧骨架监督**：Pose Head 作用于 frame-level hidden states，velocity loss 有明确物理含义。
10. **Memory Compressor 内部维度冻结为 1024**：Event Token 3584→1024 压缩，在低维空间完成 2 层 Query Compressor，再投回 LLM 空间。
11. **Memory Merge 改为 Token 语义相似度主导**：不再以生成文本标签作为主判据。
12. **Level 1/2 也显式生成 retrieval key**：统一复用 Semantic Projection 空间。
13. **文本对齐/检索不再使用 input embedding mean-pooling**：文本经过冻结 LLM 前 4 层，再进入共享语义投影头。
14. **开放语义表述收紧**：默认 claim 为 category-agnostic semantic transition；只有 unseen-action 实验证实后再使用 open-set/open-vocabulary。
15. **隐私表述收紧**：仅声称 commit 后丢弃原始雷达、减少低层感知数据长期留存风险，不宣称 Event Token 不含身份信息。
16. **Attention 仅作诊断信号**：不再将注意力权重直接等价为 hallucination detector。
17. **Fork-and-Replay 改为 Fork-and-Shadow**：proposal 后保留冻结 Active Reference，同时并行维护 Candidate 与 Shadow Active；Reject 时直接由 Shadow 接管，不再串行 replay 8~10 个 update，消除实时延迟尖峰。
18. **Commit 改为“在线控制提交 + 异步语义定稿”**：Confirm 后立即完成状态切换；旧事件的 Commit Refiner、Memory 最终写入和完整 LLM caption 进入低优先级异步队列，不阻塞 5 Hz Streaming Path。
19. **新增实时执行预算**：正常状态每 update 只运行 1 次 Event Former；Candidate 状态运行 Candidate + Shadow 两次 Event Former；以 200 ms 周期为硬预算，目标 P95 正常路径 <70 ms、Candidate 双路径 <140 ms（均为工程目标，需目标 GPU 实测）。
20. **完整 LLM 必须常驻目标 GPU/推理设备**：禁止每个 update 在 CPU/GPU 之间装载模型；完整 LLM 仅在 commit caption 或用户查询时运行，其生成过程不得阻塞 Streaming Queue。

# 一、任务目标与问题定义

面向**单人室内连续毫米波人体行为理解**。输入为持续到来的毫米波雷达流，系统需要在线维护“当前行为事件”的语义状态，在动作语义确实发生转变后形成新事件，并最终按时间顺序生成自然语言描述与长期行为总结。

系统需要解决三个核心问题：

1. **什么时候可能发生动作变化？**
2. **当前语义是否已经稳定地转变为新的事件？**
3. **已经完成的事件如何长期保存，使 LLM 可以在有限上下文中理解完整行为历史？**

核心思想：

> **事件边界不是先被显式切出来再做理解，而是在持续维护语义状态的过程中自然形成。**

## 1.1 三条设计原则

1. **Token 是长期信息的唯一货币**：原始雷达只在事件形成阶段参与计算；事件 commit 后只长期保留 Event Semantic Tokens、时间、置信度和文本元数据。
2. **语义一致性优先于帧级精确边界**：允许约 0.5–1.2 s 的语义确认延迟，优先降低过分割并提高事件语义纯度。
3. **Propose-and-Verify 职责分离**：
   - Physical Change → Proposal；
   - Semantic Change → Verify；
   - Commit 后的 Event Tokens → Memory + LLM。

## 2.2 学习视角：三个核心可学习模块

$$

\boxed{\text{Hierarchical Memory Compressor}}

# 三、时间粒度与在线更新规格

雷达帧率默认：

$$
20 \text{ fps}
$$

系统每收到 4 个新帧更新一次：

$$
\Delta t = 0.2s,\qquad 5Hz
$$

每次更新只计算新增 4 帧；Causal TCN 保持 stateful hidden state，因此不重复计算历史。

```text
20 fps radar
   ↓
4 new frames / update
   ↓
5 semantic updates / second
```

采用 5 Hz 的原因：

- Candidate 预热 1–2 次更新仅需 0.2–0.4 s；
- Verify 连续 2 次成立约需 0.4 s；
- 总体确认延迟更容易控制在约 0.5–1.2 s；
- 比 2.5 Hz 更适合短过渡动作。

2.5 Hz 作为效率消融，不作为默认配置。

# 四、模块①：Streaming Radar Encoder

## 4.1 总体结构

```text
                         4 个新雷达帧
                              │
               ┌──────────────┴──────────────┐
               ↓                             ↓
           RD Frames                    Point Frames
               │                             │
         2D CNN Encoder                PointNet Encoder
               │                             │
       frame-level r_i ∈ R256        frame-level p_i ∈ R256
               │                             │
         Stateful Causal TCN          Stateful Causal TCN
         dilation 1/2/4/8             dilation 1/2/4/8
               │                             │
       2 learnable queries            2 learnable queries
       pool newest states             pool newest states
               │                             │
          2 RD tokens                    2 PC tokens
               └──────────────┬──────────────┘
                              │
                     modality embedding
                              │
                    Transformer × 2
                              │
                  F_t ∈ R^{4×256}
```

## 4.2 RD 分支

每帧 RD 图：

```text
Input: 2×64×64
→ ConvBlock 32
→ ConvBlock 64
→ ConvBlock 128
→ ConvBlock 256
→ frame feature r_i ∈ R256
```

每个 ConvBlock：

```text
Conv 3×3 → BatchNorm → GELU → Downsample
```

4 个新帧的 frame features 进入 stateful Causal TCN：

```text
TCN Block ×4
kernel=3
dilation = 1,2,4,8
depthwise conv → pointwise conv → GELU → residual
```

随后用 2 个 learnable pooling queries 从当前新帧对应的 TCN states 中读出 2 个 RD tokens。

## 4.3 Point Cloud 分支

默认使用 **PointNet**，不默认使用 Point Transformer。

每帧点云：

$$
P_i\in \mathbb R^{N_i\times 6}
$$

每点特征：

$$
(x,y,z,v,I,SNR)
$$

结构：

```text
Shared MLP: 6→64→128→256
→ max pooling
→ p_i ∈ R256
```

4 个新帧的 $p_i$ 再进入与 RD 分支相同的 Stateful Causal TCN，最后由 2 个 learnable pooling queries 得到 2 个 Point tokens。

Point Transformer Lite 仅保留为：

- Stage 1 pose 性能不足时升级项；
- backbone 消融项。

## 4.4 融合

最终：

$$
F_t=[R_t^1,R_t^2,P_t^1,P_t^2]\in\mathbb R^{4\times256}
$$

加入：

- modality embedding；
- update-time embedding；

再经过 2 层小型 Transformer 融合。

**F_t 始终停留在 Radar Feature Space，不预投影到 LLM 维度。**

# 五、Stage 1：逐帧 Pose-Guided Radar Pretraining

Stage 1 的目的不是训练姿态模型，而是让 Radar Encoder 学到人体结构和运动动力学。

在两分支 TCN 的 frame-level hidden states 融合后，对每个雷达帧预测 3D skeleton：

$$
h_i^{frame}\in\mathbb R^{256}
$$

$$
\hat S_i=\text{PoseHead}(h_i^{frame})
$$

其中：

```text
PoseHead:
256 → 512 → J×3
```

损失：

$$
L_{pose}=L_{MPJPE}+\lambda_vL_{velocity}
$$

$$
L_{velocity}
=
\frac1{T-1}\sum_i
\|
(\hat S_i-\hat S_{i-1})-(S_i-S_{i-1})
\|_1
$$

这样 velocity loss 明确对应真实帧间人体运动。

Stage 1 完成后：

> **Pose Head 整体删除。**

推理阶段仅使用毫米波。

# 六、变化检测前端

## 6.1 Local Change Detector

先对 $F_t$ 做 LayerNorm：

$$
\bar F_t=LN(F_t)
$$

逐 token 构造：

$$
D_t=\left[\bar F_t-\bar F_{t-1},\ |\bar F_t-\bar F_{t-1}|,\ \bar F_t\odot\bar F_{t-1}\right]\in\mathbb R^{4\times768}
$$

结构：

```text
Linear 768→128
→ GELU
→ Attention Pooling over 4 tokens
→ Linear 128→64→1
→ sigmoid
```

得到：

$$
s_t^{local}
$$

定位：

> 对短时突变高敏感、高召回、允许误报，只负责提出“可能变化”。

## 6.2 Radar Transition Detector

先建立独立 Motion Prototype Space：

$$
r_t=\text{MLP}_{256\rightarrow128}(Pool(F_t))
$$

并 L2 normalize。

维护 $R_{slow}$ 为事件内 Welford running mean/variance。

维护：

$$
R_{fast,t}
=
\alpha R_{fast,t-1}
+
(1-\alpha)r_t
$$

其中：

$$
\alpha=\exp(-\Delta t/\tau_{fast})
$$

默认：

$$
\tau_{fast}=2s
$$

在 5 Hz 下：

$$
\alpha\approx0.905
$$

计算：

$$
\delta_t=
\frac{R_{fast}-R_{slow}}
{\sqrt{\sigma^2+\epsilon}}
$$

构造：

$$
Z_t=\left[R_{fast},\ R_{slow},\ |\delta_t|,\ R_{fast}\odot R_{slow},\ 1-\cos(R_{fast},R_{slow}),\ age\right]
$$

经过：

```text
MLP → 128 → 32 → 1 → sigmoid
```

得到：

$$
s_t^{radar}
$$

## 6.3 Proposal：只由物理证据产生

$$
p_t^{proposal}
=
1-(1-s_t^{local})(1-s_t^{radar})
$$

若：

$$
p_t^{proposal}>\tau_p
$$

连续 1–2 次更新，则触发 Candidate。

此时记录 $t_p$ 并执行 Fork。

**从 Candidate 建立开始，Local/Radar 不再参与 Confirm。**

# 七、Fork-and-Shadow 状态管理

Fork 的目标同时满足两件事：

1. **语义参照必须冻结**：Candidate 的 $p^{diff}$ 始终与 proposal 时刻的旧 Active 比较，避免参照系继续漂移；
2. **Reject 恢复不能依赖串行 replay**：5 Hz 下 1.5~2 s Candidate 会积累约 8~10 个 update，若 Reject 后逐步 replay，会产生数百毫秒级延迟尖峰。

因此 proposal 后保留三个逻辑状态，但**三者完全共享同一套 Event Former 参数**：

```text
                      proposal at t_p
                            │
              ┌─────────────┼─────────────┐
              ↓             ↓             ↓
       Frozen Active     Candidate      Shadow Active
        Reference          State         Recovery State
              │             │             │
       不再更新，只作     P_base启动      从旧Active快照继续
       semantic reference  吸收新雷达     吸收相同F_t
```

## 7.1 Proposal 时刻

执行：

1. 冻结语义参照：
   $$
E_A^{ref}=E_A,\qquad z_A^{ref}=g(E_A^{ref})
$$
2. 保存旧事件物理统计快照：
   $$
R_A^{snap},n_A,\mu_A,M2_A
$$
3. 旧 Active 的事件 buffer 在 $t_p$ 处封口，旧事件时间范围固定为 $[t_0,t_p]$；
4. Candidate：
   $$
E_C=P_{base}
$$
   从 $t_p$ 后独立吸收 $F_t$，并维护自身 $R^C$；
5. Shadow Active：
   $$
E_S(t_p)=E_A^{ref}
$$
   从同一旧 Active 快照继续吸收 $t_p$ 后的 $F_t$，同时继续更新旧事件的 $R_{fast}/R_{slow}/$Welford 统计；
6. Frozen Active Reference 不再运行 Event Former，只保存 $E_A^{ref}$、$z_A^{ref}$ 与封口后的旧事件 buffer。

Candidate 与 Shadow 使用**同一个 Radar Encoder 输出 $F_t$**，不重复运行 Radar Encoder。额外开销主要来自第二次 Event Former 前向。

## 7.2 Candidate 跟踪期间

- $p^{diff}$ 始终比较：
  $$
z_A^{ref}\quad\text{vs.}\quad z_C
$$
- Stability 只计算 Candidate 自身；
- Local/Radar 已完成 Proposal 职责，不再进入 Confirm；
- Candidate 的 $R^C$ 只用于 Confirm 后作为新事件的物理原型起点；
- Shadow 不参与 $p^{diff}$、Stability、Verify，也绝不被 commit；它只负责 Reject 时的无损恢复。

## 7.3 Reject

若 Candidate 被判定为与旧 Active 语义相同：

$$
E_A \leftarrow E_S
$$

并直接接管 Shadow 的：

- Event State；
- $R_{fast}$；
- $R_{slow}$；
- Welford $n/\mu/M2$。

Candidate 丢弃。

因此 Reject 是近似 $O(1)$ 的状态切换，不再执行 $F_{t_p:t}$ 的串行 replay。

## 7.4 Confirm

若 Candidate 被确认：

- 新 Active：
  $$
E_{new}^A=E_C
$$
  $$
R_{new}^A=R^C
$$
- 新事件：
  $$
t_{start}=t_p
$$
- 旧事件：
  $$
t_{end}=t_p
$$
- Shadow 丢弃；
- 旧事件 $[F_{t_0},\dots,F_{t_p}]$ 已经封口，进入**异步语义定稿队列**；
- Streaming Path 立即继续处理新 Active，不等待 Commit Refiner 或 caption generation。

因此系统区分两种“commit”：

1. **Online Control Commit**：Confirm 后立即完成事件切换，属于实时控制路径；
2. **Semantic Finalization**：Commit Refiner、最终 Memory Token 更新和 caption 生成，属于异步低优先级路径。

# 八、模块②：Streaming Semantic Event Former

这是整个系统的核心。

## 8.1 Event State

初始化：

$$
P_{base}\in\mathbb R^{K\times d_{LLM}}
$$

默认：

$$
K=8
$$

若使用 Qwen2.5-7B：

$$
d_{LLM}=3584
$$

因此：

$$
E_t\in\mathbb R^{8\times3584}
$$

## 8.2 固定 Event Prompt

Streaming Path 不接受任意用户问题。

只使用固定语义提示，例如：

> Maintain a compact semantic representation of the current human motion event from radar observations.

该 Prompt 在整个会话固定，其前 4 层 K/V 可缓存。

因此：

$$
Radar\rightarrow Event\ State
$$

保持 query-independent。

真正用户问题只进入 Reasoning Path：

$$
Query+Memory\rightarrow Full\ LLM
$$

# 九、Event Former 内部结构

## 9.1 Prefix-LM Mask

Instruction/Event Prompt 保持正常 causal mask。

8 个 Event Tokens 之间：

> **双向全连接。**

因为它们是并列 memory slots，不是自然语言序列。

## 9.2 LLM 层 1–4

主干：

- 冻结；
- LoRA 插入 q/v；
- rank = 16 默认。

每层：

```text
Native Self-Attention
        ↓
Bottleneck Radar Cross-Attention
        ↓
Native FFN
```

## 9.3 512 维 Bottleneck Cross-Attention

不在完整 3584 维执行雷达注意力。

定义：

$$
Q=W_QE,\quad K=W_KF_t,\quad V=W_VF_t
$$

其中：

$$
W_Q:\mathbb R^{3584}\rightarrow\mathbb R^{512}
$$

$$
W_K,W_V:\mathbb R^{256}\rightarrow\mathbb R^{512}
$$

在 512 维多头注意力：

$$
C_t=MHA(Q_{512},K_{512},V_{512})
$$

再：

$$
W_O:\mathbb R^{512}\rightarrow\mathbb R^{3584}
$$

层内更新：

$$
H^l=H^l+\tanh(\alpha_l)W_OC_t
$$

其中：

$$
\alpha_l=0
$$

初始化。

每层新增参数约 4M，4 层约 16M 量级，而不是百 M 级。

# 十、[跨 update Event State 更新](事件token的更新机制)

第 4 层得到：

$$
H_t^4
$$

经：

$$
\hat E_t=W_{out}(H_t^4)
$$

其中：

$$
W_{out}:\mathbb R^{3584}\rightarrow\mathbb R^{3584}
$$

采用 identity-like initialization。

构造：

$$
\Delta E_t=\hat E_t-E_{t-1}
$$

每个 Event Token 生成一个标量 gate：

$$
\lambda_{t,k}=MLP([LN(E_{t-1,k});LN(\Delta E_{t,k});maturity_t])\in\mathbb R
$$

最终：

$$
E_{t,k}=E_{t-1,k}+\tanh(\lambda_{t,k})\Delta E_{t,k}
$$

每个 token 决定“这一时刻我要更新多少”，而不是为每个 hidden dimension 单独生成 gate。

训练/调试必须记录：

$$
\|E_t\|
$$

随时间曲线，监控状态范数漂移。

# 十一、Semantic Projection 与文本语义空间

## 11.1 Event Semantic Projection

输入 Event Tokens：

$$
E\in\mathbb R^{K\times3584}
$$

使用一个 learnable semantic query $q_s$：

$$
h_E=Attention(q_s,E,E)
$$

再：

```text
3584 → 256 → 128
→ L2 Normalize
```

得到：

$$
z_E\in\mathbb R^{128}
$$

Active 与 Candidate 共享同一个 Projection Head：

$$
z_A=g(E_A),\qquad z_C=g(E_C)
$$

## 11.2 Text Semantic Projection

不再使用 input embeddings mean-pooling。

文本：

```text
Text Tokens
    ↓
Frozen LLM Layers 1–4
    ↓
Hidden States
    ↓
同一个 Semantic Query Pooling + Projection g(·)
    ↓
z_text ∈ R128
```

这样：

- Event semantic key；
- text query；
- retrieval；
- semantic alignment；

全部闭合在同一个 $z$ 空间。

# 十二、Semantic Difference

构造：

$$
D_t=[z_A,z_C,|z_A-z_C|,z_A\odot z_C,1-\cos(z_A,z_C),maturity]
$$

输入维度约 514。

结构：

```text
514 → 256 → 64 → 1
```

中间使用 GELU 和 Dropout(0.1)。

输出：

$$
p_t^{diff}
$$

训练采用成熟度 2×2 pairing：

| Pair | Label |
|---|---|
| mature(A) vs nascent(A) | same |
| mature(A) vs mature(A') | same |
| mature(A) vs nascent(B) | different |
| mature(A) vs mature(B) | different |

目标是训练：

> **category-agnostic semantic difference**

而不是默认宣称 open-vocabulary。

---

# 十三、Candidate Stability：无参数版本

不再使用 learned Stability Head。

最近三个 Candidate semantic vectors：

$$
z_t,z_{t-1},z_{t-2}
$$

计算：

$$
c_1=\cos(z_t,z_{t-1})
$$

$$
c_2=\cos(z_t,z_{t-2})
$$

$$
v_t=\frac13\sum_{j=t-2}^{t}\|z_j-\bar z\|_2^2
$$

定义：

$$
s_t^{stable}=\frac{c_1+c_2}{2}\cdot\exp(-v_t/\tau_s)
$$

裁剪至 $[0,1]$。

它只衡量：

> Candidate 是否已形成稳定语义状态。

不需要额外 GT，也不引入额外训练损失。

---

# 十四、Semantic Verify

Candidate 建立后，Local/Radar 退出 Confirm 判决。

Verify 输入：

$$
u_t=[p_t^{diff},s_t^{stable},maturity_t]
$$

采用极小的单调 Logistic Head：

$$
p_t^{verify}=\sigma(w_dp_t^{diff}+w_ss_t^{stable}+w_mmaturity_t+b)
$$

其中：

$$
w_i=\text{softplus}(\hat w_i)\ge0
$$

因此：

- semantic difference 越强；
- Candidate 越稳定；
- Candidate 越成熟；

不会反而降低确认概率。

## Confirm

满足：

$$
p_t^{verify}>\tau_c
$$

连续 2 次更新：Confirm。

## Reject

Candidate 已运行超过 $1.5\sim2s$ 且 $p_t^{diff}<\tau_r$ 持续低位：Reject。

# 十五、Commit Refiner

不新增独立网络，复用 Streaming Semantic Event Former。

**Commit Refiner 不属于 200 ms Streaming Critical Path。** Confirm 后旧事件先完成 Online Control Commit，随后将封口后的事件 buffer 送入低优先级 Finalization Queue。Streaming Path 立即处理新 Active，不等待定稿。

## 15.1 Streaming Mode

$$
E_{t-1}\xrightarrow{F_t}E_t
$$

每次只读当前更新的 $F_t$。

## 15.2 Commit Mode

旧事件完整 buffer：

$$
[F_1,F_2,\dots,F_T]
$$

加入事件相对时间编码：

$$
F_i\leftarrow F_i+PE(i/T)
$$

其中：

$$
i/T\in[0,1]
$$

再：

$$
P_{base}\xrightarrow{F_{1:T}}E_{commit}
$$

Commit 时允许 Event Tokens 对整个事件 radar tokens 非因果 cross-attention。

事件过长时按时间池化至最多 256 radar tokens。

## 15.3 Provisional → Refined Memory

Confirm 时可以先写入一个 provisional memory unit：

$$
E_i^{prov}=E_A^{ref}
$$

使新近历史立即可被查询。

异步 Commit Refiner 完成后：

$$
E_i^{prov}
\rightarrow E_i^{commit}
$$

并重新计算：

$$
k_i=g(E_i^{commit})
$$

完成原子替换。caption $y_i$ 可更晚写入，因此文本不是实时状态切换的前置条件。

---

# 十六、Stage 2 同时训练 Streaming / Commit 两种视图

对每个完整事件同时构造：

## Streaming View

$$
F_1\rightarrow F_2\rightarrow\dots\rightarrow F_T
$$

得到：

$$
E_{stream}
$$

## Commit View

$$
[F_1,\dots,F_T]
$$

一次编码得到：

$$
E_{commit}
$$

二者分别生成：

$$
z_{stream},z_{commit}
$$

加入一致性损失：

$$
L_{cons}=1-\cos(z_{stream},z_{commit})
$$

Stage 2 总损失：

$$
L_{stage2}=L_{text}+\lambda_aL_{align}+\lambda_cL_{cons}
$$

其中：

- $L_{text}$：Event Tokens 驱动完整 LLM 生成 GT caption；
- $L_{align}$：$z_E$ 与 $z_{text}$ 对齐；
- $L_{cons}$：streaming/commit 两种编码模式语义一致。

# 十七、Idle / Presence Controller

Idle 保持非深度学习控制器。

输入：

$$
[N_{points},E_{RD},E_{dynamic},tracker\ confidence]
$$

经标准化后计算简单 presence score，并使用双阈值迟滞：

```text
Idle   -- score > τ_enter --> Active
Active -- score < τ_exit for N updates --> Idle
```

要求：

$$
\tau_{enter}>\tau_{exit}
$$

关键约束：

> **静止站立 ≠ Idle。**

因此不能只看 Doppler。

Idle 时：

- Active 暂停更新；
- 不触发新 proposal；
- 在途 Candidate 丢弃。

短中断恢复窗口默认 2s，超过则从 $P_{base}$ 开启新事件。

# 十八、实时执行与异步调度

## 18.1 每 0.2 s 的 Critical Path

正常 Active 状态每次 update 只执行：

```text
4 个新雷达帧
→ Radar Encoder
→ Local / Radar Proposal Heads
→ LLM Layer 1–4 + 512-d Bottleneck Cross-Attention
→ Event State Update
→ Semantic Projection
```

不执行：

- LLM Layer 5–28；
- Memory Compressor；
- Full LLM caption；
- 长历史 reasoning。

以 Qwen2.5-7B 量级、$K=8$ 为例，粗略数量级：

- 前 4 层 LLM：约 $15$ GFLOPs / update；
- 4 层 512-d bottleneck cross-attention：约 $0.2\sim0.3$ GFLOPs / update；
- Radar Encoder + TCN + Fusion + heads：约 $1\sim2$ GFLOPs / update。

因此正常路径总量约：

$$
16\sim18\ \text{GFLOPs/update}
$$

5 Hz 对应：

$$
80\sim90\ \text{GFLOPs/s}
$$

该估算只用于确定数量级；真实时延由显存带宽、kernel launch、实现框架和目标 GPU 决定，论文必须报告实测 P50/P95。

## 18.2 Candidate 状态计算预算

Candidate 活跃时：

- Radar Encoder 仍然只运行 **1 次**；
- Frozen Active Reference 不运行网络；
- Candidate Event Former 运行 1 次；
- Shadow Active Event Former 再运行 1 次。

因此 Candidate 期间主要是 Event Former 约 2× 计算，但避免 Reject 后 8~10 次串行 replay 的突发延迟。

工程目标：

| 路径 | P95 目标预算 |
|---|---:|
| Radar Encoder | < 10 ms |
| 单次 Event Former（LLM 1–4 + cross-attn） | < 50 ms |
| heads / projection / state logic | < 10 ms |
| 正常 Active 总路径 | **< 70 ms** |
| Candidate + Shadow 双路径 | **< 140 ms** |
| Streaming 周期 | **200 ms** |

这些数字是**设计目标而非已验证结果**；最终以目标 GPU 的实测为准。若 Candidate P95 超过 200 ms，优先按顺序降级：

1. cross-attention bottleneck 512→256；
2. LLM streaming layers 4→2；
3. K=8→4；
4. update rate 5 Hz→2.5 Hz（最后手段）。

## 18.3 双队列调度

系统使用逻辑上的两级队列：

### High-Priority Streaming Queue

每 200 ms 处理一次：

- Radar Encoder；
- Active / Candidate / Shadow Event State；
- Proposal / Verify；
- Presence。

**任何异步任务都不得阻塞此队列。**

### Low-Priority Finalization / Reasoning Queue

处理：

- Commit Refiner；
- Memory Compressor；
- Full LLM caption；
- 用户长历史查询。

Confirm 时只把旧事件封口并提交 job，不同步等待结果。

实现上可采用：

- 独立 worker / process；
- 独立 CUDA stream（若框架与硬件支持有效调度）；
- 或统一 scheduler 中对 Streaming Job 赋更高优先级。

不依赖“GPU 一定能硬件抢占”的假设；真正要求是应用层调度保证 Streaming Job 先获得计算资源。

## 18.4 模型驻留约束

完整 LLM 权重必须在实时会话期间常驻目标推理设备。

禁止每个 0.2 s update：

```text
CPU → GPU load LLM layers
```

Streaming Path 只调用 Layer 1–4；Commit caption / 用户 Query 才继续调用后续层。

## 18.5 异步队列过载保护

若 Finalization Queue 积压：

1. **首先延后 caption generation**；
2. Commit Refiner 优先于文本生成；
3. provisional Event Token 仍可用于近期 memory/query；
4. 队列长度、finalization latency、caption lag 必须作为系统监控指标。

# 十九、Hierarchical Event Memory

## 19.1 Memory Unit

$$
M_i=\{E_i,T_i,c_i,k_i,y_i,status_i\}
$$

其中：

- $E_i$：8×3584 Event Tokens；
- $T_i$：start/end/confirm；
- $c_i$：confidence；
- $k_i$：128-d semantic retrieval key；
- $y_i$：commit caption，可异步补写；
- $status_i$：`provisional / refined / captioned`，用于标记异步定稿状态。

## 19.2 Level 0

最近 8 个完整事件。

Level 0 保留完整 Event Tokens。

## 19.3 Query Compressor：内部维度 1024

输入：

$$
E\in\mathbb R^{N\times3584}
$$

先：

$$
3584\rightarrow1024
$$

得到 $\tilde E$。

加入：

- Event Position Embedding；
- Token Position Embedding；
- Time Embedding；
- Level Embedding。

初始化：

$$
S_0\in\mathbb R^{4\times1024}
$$

执行：

```text
Transformer Decoder ×2

Summary Self-Attention
→ Cross-Attention to compressed event tokens
→ FFN
```

FFN：

$$
1024\rightarrow4096\rightarrow1024
$$

输出：

$$
S\in\mathbb R^{4\times1024}
$$

再投影回：

$$
1024\rightarrow3584
$$

得到 4 个 Summary Event Tokens。

Level 0→1 与 Level 1→2 共享同一套 Compressor 参数。

# 二十、Memory Merge

同类事件合并不再由生成文本主导。

主判据：

$$
\cos(k_{prev},k_{new})>\tau_{merge}
$$

并同时满足：

$$
gap<\tau_{gap}
$$

且期间无其他 confirmed event，则合并。

文本 $y$ 仅用于可读性检查、辅助诊断和最终叙述，不作为 memory structure 的主要控制信号。

合并后：

- tokens 经 Compressor 合并；
- time range 合并；
- confidence 取 min；
- metadata 保存 count。

# 二十一、Memory Retrieval

## 21.1 Level 0

全部读取，不检索。

## 21.2 Level 1 / Level 2

每个 summary unit 都通过同一个 Semantic Projection Head 生成 key：

$$
k_i^{L1}=g(S_i^{L1})
$$

$$
k_i^{L2}=g(S_i^{L2})
$$

查询文本：

```text
Query
→ Frozen LLM 1–4
→ shared g(·)
→ z_q
```

排序：

$$
s_i=\cos(z_q,k_i)+\beta e^{-\Delta t_i/\tau}+\gamma c_i
$$

默认：

- Level 1：Top-2；
- Level 2：Top-1。

若 retrieval probe 不达标，再增加轻量 text-event contrastive loss；不新增 Retrieval Encoder。

# 二十二、完整 LLM 推理路径

Reasoning Path 输入：

```text
[Retrieved Level-2 Summary Tokens]
→ [Retrieved Level-1 Summary Tokens]
→ [All Level-0 Event Tokens]
→ [Current Event Tokens, optional]
→ [User Query]
```

完整 LLM：

- 不读取 raw radar；
- 不读取历史 radar features；
- 只读取 Event/Memory Tokens；
- 若最近事件仍处于 provisional 状态，可先使用 $E_i^{prov}$，待异步 Refiner 完成后自动替换为 $E_i^{commit}$。

# 二十三、训练流程

## Stage 1：Radar Motion Pretraining

训练 Radar Encoder + 临时 Pose Head。

$$
L_{pose}=L_{MPJPE}+\lambda_vL_{velocity}
$$

Stage 1 后删除 Pose Head。

## Stage 2：Radar→Language Semantic Event Alignment

训练：

- LLM 1–4 LoRA；
- 512-d bottleneck cross-attention；
- W_out；
- scalar state gate；
- Semantic Projection。

冻结 LLM backbone 主参数。

损失：

$$
L_{stage2}=L_{text}+\lambda_aL_{align}+\lambda_cL_{cons}
$$

同时训练 streaming view 与 commit view，使用固定 Event Prompt。

## Stage 3：Continuous Transition Learning

训练：

- Local Change Head；
- Radar Transition Head；
- Semantic Difference Head；
- Verify Logistic Head。

损失：

$$
L_{stage3}=\lambda_1L_{local}+\lambda_2L_{radar}+\lambda_3L_{semantic}+\lambda_4L_{verify}
$$

不包含 Stability Loss。

边界标签：容差区间 → chunk-level Gaussian soft label。

## Stage 4：Hierarchical Memory Compression

前端冻结。

训练 1024-d Query Compressor 与 in/out projection。

$$
L_{memory}=L_{summary}+\lambda_rL_{retain}
$$

其中：

$$
L_{retain}=1-\cos(z_{summary},z_{source-group})
$$

## Stage 5：可选 Joint Fine-tuning

只在前四阶段稳定后进行；若无明显收益则不做。

# 二十八、论文核心 Claim

一句话：

> **A continuously updated, language-aligned event representation simultaneously serves as the streaming semantic state, the basis for semantic transition verification, the long-term memory unit, and the direct input to LLM reasoning.**

中文：

> **同一组语言对齐的 Event Semantic Tokens 同时承担流式事件状态、语义转换判决基底、长期记忆单元和 LLM 推理输入四种角色。**

三个主要贡献：

1. **Continuous Semantic Event Formation**：Physical Proposal + Semantic Verify + Fork-and-Shadow，使事件边界成为持续语义理解的副产品，同时避免 Reject replay 的实时延迟尖峰。
2. **Persistent Language-Aligned Event Tokens**：Event Token 从流式状态直接转化为长期记忆，实现感知、事件形成和 LLM 推理之间的统一接口。
3. **Hierarchical Token Memory for Long Streams**：共享 Query Compressor 对变旧事件逐级压缩，在保持语义的同时控制上下文成本。
